# 两条授权线路的通用恢复与探测节流

日期：2026-10-23，北京时间。接续 `remote-recovery-20261023.md` 的修复。

## 本轮修改

- 线路以规范 Origin 标识，测量、状态隔离与 UI 不再使用服务商名称作为键。界面按发现顺序显示“线路1”“线路2”。同服务商的两个不同 Origin 不会互相覆盖。
- 前端选线、失败隔离、恢复探测、读取切线和事件流切换使用相同规则；原生通知发现也复用统一通道来源校验，修复仅接受 ngrok 作为备用地址的遗漏。
- 保留接入协议需要的提示页请求头、Cookie 适配，以及原有 HTTPS、允许来源、Bearer、服务器身份和幂等校验。这些适配不决定线路优先级，未开放任意外部域名接收凭证。
- 当前尝试失败后，重复安全的只读操作顺序尝试另一条授权线路；已知有健康备用线路时，沉默 8 秒即可接替。网络明确失败无需等满 8 秒。
- 尚未结束的逐线路测速继续合并；健康备用线路最多每 15 秒补测一次。活动线路仍请求真实会话状态，不用旧响应作为业务读取结果。
- 失败后按 15、30、60 秒冷却，之后以 60 秒封顶。冷却到期先探测，成功后才重新承担业务，不凭过期的低延迟数值立即接回。
- 前端收到 429 或有效 `Retry-After` 时，按服务端期限冷却；并发成功、迟到响应、通道凭证轮换均不能提前清除该期限。
- 后台或离线页面不启动新的网页主动测速。已有后台通知连接和桌面可达性检查各自保留原生命周期。
- 事件流对小幅 RTT 抖动保持现有健康连接：改善不足 150 毫秒或原线路 RTT 的 20% 时不因该小幅差异重连。明确故障仍立即选择另一条健康线路。
- 原生通知重连保留 1、2、4、8、16、30 秒的有限退避及 60 秒 discovery 周期，没有增加同一 Origin 的重复订阅。
- 问答、审批和消息动作保持单次提交。故障隔离后新动作走存活线路；已发出动作通过既有幂等与回执机制确认，不能把未知结果当作未执行而重复提交。

## 修复的并发边界

- 备用通道 401 保留 `secondaryChannel`，不被前端误当作主入口登录失效。
- 测速与业务完成结果按序应用，旧探测成功不会覆盖更新的失败，旧探测失败也不会覆盖更新的成功。
- 主动取消不更新失败冷却，也不触发新设备或新授权范围下的请求。
- 备用线路健康但尚未到补测时间时，活动线路失败仍立即请求备用线路的真实状态；活动线路沉默时在 8 秒后接替。
- 429 的冷却独立于网络健康恢复。较早请求迟到返回限流时仍尊重其期限；较新动作成功不会清掉已确定的限流。

## 测速和官方限额

网页测速是读取 `/api/session` 的 HTTP 请求，不是发送会话消息。正常前台状态轮询每 15 秒执行一次，常规情况下每条线路约 4 次/分钟；额外的真实状态读取、故障接替、图片及消息等业务请求另外计数。新规则限制的是额外备用探测，不通过缓存旧状态削减必要的业务读取。

桌面 zrok 适配自身还按 30 秒周期检查公共可达性，正常约 2 次/分钟；手机网页后台暂停不等于所有桌面和原生网络活动停止。

2026-10-23 查证的 myzrok 官方公共分享前端限额为：

| 限制对象 | 公开阈值 |
| --- | --- |
| 每个 IP | 每 5 分钟 2,000 个请求 |
| 每个分享 | 每 5 分钟 7,500 个请求 |

另有按账户方案区分的带宽限制。原有日志不足以证明此前故障由上述限流造成；手机日志中的无响应和电脑 TLS 超时不能直接等同于 HTTP 限流。
