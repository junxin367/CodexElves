# 远程会话模型与推理等级原生链路核查

日期：2026-10-18（Asia/Shanghai）。

状态：**PASS**。已修复原生桥的四类问题；当前生产 `native.js` 在隔离运行环境中通过 **41/41** 项回归。未对真实会话写设置、发送消息或发起付费推理；结果不代表真实模型执行验收。

## RCA 结论

- 状态：已确认。结论限于本次可复放的参数传递、设置应用、拒绝处理与读取逻辑。
- 现象：从有推理等级的模型切换到不声明推理等级的模型时，普通发送及两种队列仍把旧 `high` 写入下一轮；原生设置返回 `false` 后，普通发送、队列和目标仍可能继续提交；普通发送的设置更新抛错被表述为消息送达未知；`thread/read` 的明确 `null` 等级会被旧缓存值覆盖。
- 直接原因：普通发送把未提供的等级交给原生 `Pln`，后者继承 `latestReasoningEffort`；队列自身也使用同一回退。原生 `Pln`、`Q6t` 与桥接队列均未检查设置更新的布尔结果。会话读取的 `??` 链把明确的 `null` 当成缺失字段。
- 根因：桥接未区分“没有选择设置”“换模型后清除旧等级”和“当前字段明确为空”，也未在所有提交分支建立设置应用成功的前置条件。
- 系统性根因：普通发送、排队、目标和编辑分别解析设置及处理更新回执，导致编辑/目标已有的换模型清空逻辑没有覆盖普通发送/队列，编辑已有的 `false` 拒绝也没有覆盖其余提交入口。各分支此前使用不同的会话配置读取顺序。
- 关键因果链：网页仅提交无推理模型的 `model` → 桥接未明确清空等级 → 原生继承旧 `high` → 下一轮设置仍含旧等级；或设置接口返回 `false` → 调用方忽略回执 → 继续准备、发送或创建目标。修复后分别在解析阶段产生明确 `null`，并在提交前拦截失败。

## 已排除解释

- 前端漏传显式模型/等级：生产网页的隔离 Chrome 记录由主代理保存在同目录浏览器证据中。本轮原生回归独立传入相同类型载荷；问题可在前端之外复现。
- `collaborationMode` 固定覆盖新模型：实际 `xV/rnn` 会同步模型与等级；显式双字段成功更新的路径通过，因此没有改协议映射或强制替换协作模式。
- 所有模型只能使用固定推理档位：当前合同要求依原生目录，本轮保留 `max` 和有门禁的 `ultra`，没有新增按名称裁剪。
- 只要设置请求抛错就代表消息可能送达：明确设置失败时，消息提交尚未开始。本轮验证普通发送、队列、编辑和目标均无后续提交；普通发送不再提示送达未知。
