# Android 浏览器首次登录跳转空白排查与修复

## RCA 结论

- 状态：部分确认。已通过实际 HTTP 请求和生产回调代码对照验证缺陷；手机尚未运行修复后的原生代码，本次现场回调入参仍需更新 App 后确认。
- 现象：首次访问 `http://config.aaa.cn/` 页面空白，用户反馈手动刷新后才显示登录页。
- 直接原因：当首次 `onPageStarted` 报告的是重定向后的登录地址，原地址校验会提前返回；WebView 保持隐藏，`mainFrameStarted` 保持 `false`，随后的完成及主页面错误回调也会被忽略。
- 根因：`shouldOverrideUrlLoading` 已允许主页面重定向，并更新了网络来源，但没有同步 `pendingNavigationUrl`；消费者仍用原始输入地址判断新页面是否属于当前导航。
- 系统性根因：防止旧页面回调串入的检查把初始 URL 当作不变的导航身份，没有把合法主框架跳转纳入状态更新；原页面诊断位于校验通过之后，回调被拒绝时没有日志。
- 关键因果链：输入配置站点地址 → 返回 302 → 允许跳转到账号登录站点，但待加载地址仍是配置站点 → 登录地址的首次开始回调被拒绝 → 完成和错误回调继续被拒绝 → 页面保持不可见。刷新时从 `WebView.getUrl()` 取得登录地址，待加载地址与回调重新一致，因此恢复。

## 异常状态溯源

- 适用约束：在已允许当前主框架 HTTP/HTTPS 跳转、且尚未开始目标页面的前提下，待加载地址必须随该主框架目标更新；子框架和被拒绝地址不得覆盖它。
- 约束依据及状态：用户要求首次访问直接进入登录页，主框架跳转返回 `false` 表示允许 WebView 继续导航；代码验证覆盖此行为。源码场景已确认，手机实际回调入参尚缺。
- 本次运行前提命中判定：源码对照用例命中；手机日志无法直接判定回调入参。
- 场景命中证据：站点真实 302 跳转、手机两个目标主机的隧道成功记录、生产回调代码对照。
- 值判断：原始配置站点 URL 本身合法；缺陷在于合法跳转后消费者仍拿它匹配新文档，不能把合法 URL 本身视为非法输入。
- 值的实际来源与传播路径：`navigate` 从输入构造目标并写入 `pendingNavigationUrl`；WebView 允许登录跳转；原实现只更新 `networkPageOrigin`；`onPageStarted` 继续读取旧的待加载地址并拒绝回调。
- 最后满足约束的状态 → 首次约束违反点：开始导航时输入和待加载地址一致 → 允许主框架跳转时没有同步待加载地址。
- 调查边界与未知上游：原生 WebView 回调顺序由设备提供；本次未连接真机或模拟器，未以隔离执行器结果代替真实渲染结果。
