### UF-01：已通过子场景不能被笼统重新列为未完成

- 用户依据：“当前有些功能我记得你已经验证过的了”。
- 预期：同一功能分列“已通过的具体场景、尚未执行的边界、待用户验收、因代码变化需要复测”，每项关联其版本和原件。某个失败分支没验，不应写成正常发送/引导等整个功能都没验。
- 回归检查：汇总一次队列和侧边会话进度，对照原执行记录，确认已通过场景未丢失；如果需要重测，明确触发它的代码或环境变化。不能用旧正常路径补成所有异常分支已通过。
- 防止复发：维护反馈→用例→证据→交付状态的映射；本清单后续条目都沿用这一口径，不用“全部恢复”“全部未完成”代替逐项事实。

### UF-02：手机目标编辑弹窗为键盘预留空间

- 用户依据：“编辑目标弹窗的高度不要那么高……预留下部分空间给键盘使用”。
- 复现/验收：在手机尺寸页面打开已有长目标的编辑弹窗；输入正文；缩小可见区域；滚动长内容；取消再打开。真机安装后另验软键盘弹出和收起。
- 预期：弹窗不占满页面，输入区内部滚动，保存/取消始终可触达；已有正文和编辑草稿保持，不因布局变化提交或清空。历史报告中的具体高度是当时样本，不是永久固定产品尺寸。
- 防止复发：同时检查长内容、紧凑可视区域和实际软键盘。浏览器缩小视口不标记为 Android 键盘通过；后续固定高度/字号样式变动需要匹配的新布局证据。
- 证据：[手机目标专项](remote-goal-mobile-20261103.md)；本地原件 `dist/validation/remote-goal-mobile-20261103/`。

### UF-03：目标展开后的暂停/开始和删除必须执行真实动作

- 用户依据：“编辑的icon下方增加‘暂停/开始’ 删除 2个icon按钮，按钮需要能触发对应的功能逻辑”。
- 复现/验收：展开已有目标→暂停→刷新→开始→刷新→确认删除→刷新；另验证取消删除、旧目标状态已变化和结果未确认。
- 预期：编辑、状态控制、删除按既定位置排列。状态控制作用于同一目标，保留正文与创建身份；删除清除目标，不删除聊天历史，刷新不复活。受限状态不强制启动，未知结果不重复提交。
- 防止复发：不能仅验按钮存在、变灰或卡片消失；核对原生目标状态及原回执。暂停目标与停止当前生成是不同动作，不能顺带调用停止生成；不能用重新设置目标替代暂停/恢复。
- 证据：[手机目标专项](remote-goal-mobile-20261103.md)。此项用户要求已明确远程目标删除入口，较早文档“远程清除入口尚未定义”的表述只保留历史含义。

### UF-04：持续在线但会话读取失败后，不能长期停在旧显示和灰色发送

- 用户依据：“只显示比较久的会话……输入框已经有数据，但是按钮是置灰的……杀掉软件后再进去才正常”。
- 复现/验收：先有历史与草稿缓存；连接检查持续正常；令本次会话设置或最新历史读取失败，再恢复读取。保持同一页面，不杀进程、不刷新、不重发；另验首次补读失败及再次选择同一会话。
- 预期：缓存先显示，失败读取能继续恢复；拿到准确、可写的当前会话后发送恢复可用，草稿逐字保持，最新消息补齐。
- 防止复发：连接在线不等于会话读取完整；不能把缓存当成可写身份，也不能因已有缓存而永久跳过补读。复用既有恢复调度，正常会话不因此重复全文读取；原未决写回执继续保护。
- 证据：[读取恢复专项](remote-read-retry-20261103.md)。用户未记得触发时机，因此不把后台返回、侧边切换等任何单一入口写成已确认的手机根因。

### UF-05：异步读取不能关闭用户较新展开的侧栏

- 用户依据：“点击后刚弹出立刻就收回去”。
- 复现/验收：分别暂缓首次侧栏目录、切换会话缓存、新建页项目读取；等待时点击左上按钮展开侧栏，然后放行读取。另验用户主动选择会话、新建、点击遮罩时正常关闭。
- 预期：自动初始化和迟到读取不覆盖用户刚完成的展开；显式导航仍按原交互关闭。
- 防止复发：关闭时机与明确导航动作绑定，不放到异步等待结束后；不能仅测试 `closeMobileSidebar` 的空桩，也不先靠防抖、延时或额外锁遮住问题。
- 证据：[侧栏专项](remote-sidebar-open-20261103.md)；初始化浏览器对照与缓存/项目两条行为回归分别登记。

### UF-06：发出后停更与编辑置灰，要验真实生命周期入口

- 用户依据：“发出后远程会话里没有更新到……编辑这条信息的时候……发送按钮被置灰……杀掉app……才恢复正常”。
- 与 UF-04 的区别：本条有后续手机日志和导航/前后台线索。相似表现不等于同一个根因，也不能用前一条修复关闭本条。
- 复现/验收：导航被下载、取消或内置浏览器接管，原文档仍存在；经历 `beforeunload → hidden → visible`，但没有 `pagehide/pageshow`，再读取/切换会话。另验正常 `pagehide → pageshow` 和普通前后台切换。业务消息只发送一次，检查之后的接收与界面更新。
- 预期：仍存活并可见的文档恢复事件、连接检查与当前会话读取，不停留旧 `pageLeaving` 状态；草稿、历史和未知回执保持，不依赖杀 App，不通过自动重发“恢复”。
- 编辑边界：用户原话未明确编辑对象；回归分别检查未发送草稿和已有消息的编辑，不能把其中一个通过写成两者均通过。合法的只读、未决回执等禁用条件仍保留。
- 防止复发：从真实事件入口验收，不能手动调用 `resumePage()` 替代生命周期。日志不足时保留“手机现场部分确认”，不据浏览器对照声称手机全部故障已归因。
- 证据：[生命周期及诊断专项](remote-lifecycle-20261103.md)。热更新/新 APK 的交付记录与用户真机验收分开。

### UF-07：短操作由控件表达状态，长时间未确认再补充提示

- 用户依据：“只有真实操作比较久……才显示，而不是一触发对应功能就默认显示”。
- 复现/验收：分别执行快速成功、真实请求暂缓超过提示阈值、明确失败、未知回执后恢复；覆盖引导、保存、取消及同机制的消息、目标、侧边、问答和压缩入口。
- 预期：短操作先显示对应按钮的进行中状态，不抢先弹红；仍未确认时再增加简短说明，结束后还原。明确失败、授权不符和输入错误及时提示；未知回执的去重锁不能因隐藏提示而解除。
- 当前实现阈值为 **5 秒**。用户原话为“n秒”，5 秒是本轮实现选择，**不是消息/引导必须完成的 SLA**；以后若调整，需要同步更新阈值用例。
- 防止复发：同时断言提示出现时刻、按钮状态和提交次数；不能只验最终提示文字，也不能把真实失败全部延后。
- 证据：[提示与队列专项](remote-queue-feedback-20261103.md)。取消/引导延迟样本分别约 5015/5028 ms；132 项前端状态回归不是全部真实功能通过。

### UF-08：队列交互减少重复准备，不削弱消息保护

- 用户依据：“引导，编辑，取消编辑等等都很慢……之前的交互操作速度是很顺畅的”。
- 复现/验收：活动轮中加入带唯一标记的队列消息，分别开始编辑、取消恢复、保存、引导，核对顺序、准确对象与唯一接受；在同一实例记录原生处理、HTTP 和 UI 反馈的分段耗时。
- 已确认原因：已缓存模块导出，但每次定位仍重复读取同一静态依赖源码。修复复用静态资源读取及已识别的准备函数，没有删除归属/消息身份检查。
- 预期：快速操作及时完成且反馈清楚，长操作沿 UF-07 展示；不以提前伪造成功、跳过输入核对或重复提交换取速度。
- 防止复发：缓存检查要覆盖“命中之前的准备成本”；测调用次数与耗时来源，不凭代码行数推测瓶颈。失败可重新发现，新资源版本不沿用旧合同；不要把单次本机样本扩成手机平均值/P95。
- 证据：[提示与队列专项](remote-queue-feedback-20261103.md)，含真实前后计时、自然出队及 32 项队列合同回归。几毫秒的必要归属检查不作为本轮删减对象。

### UF-09：侧边成功改模型后，往返、刷新和续发保持自身模型

- 用户依据：“选择其他模型，发送信息，返回主会话再次进去侧边会话时……变会了主会话的模型”。
- 复现/验收：建立主会话 A→新建侧边继承 A→侧边选择 B 及其思考深度并成功发送→返回主会话核对 A→重进侧边核对 B→整页刷新核对 B→不重选模型继续发送，核对原生接受轮次配置仍为 B。再创建另一侧边，仍应继承主 A。
- 预期：读取完成后的侧边显示、实际后续发送及原生当前配置一致；主会话和其他侧边隔离。必须先成功发送 B，不能只测未发送的临时选择。
- 已确认原因：`runtimeThread` 无条件用创建时标签的 `lockedCollaborationMode` 覆盖侧边最新配置。真实复现中发送及连续原生轮次一直是 B，只是远程详情回显为 A；不把该证据改写成已证明“实际发送错模型”。
- 修复边界：合法侧边优先读取当前 `latestCollaborationMode.settings`，兼容 `latestThreadSettings.collaborationMode.settings`，缺失时才回退标签配置。模型和思考深度同源，保留显式 `null`；没有新增前端模型覆盖表或更改发送流程。
- 防止复发：同时检查首轮继承、发送后新配置、返回重进、整页刷新、无覆盖参数的下一条发送、主侧隔离、缺失配置及已关闭侧边；不能只看当前页面仍保留的临时模型按钮。
- 源码/回归：[native.js](../../assets/remote-access/native.js) 的 `runtimeThread`；[cdp_bridge.rs](../../crates/codex-elves-core/tests/cdp_bridge.rs) 的 `request_client_side_thread_snapshot_reads_locked_model_without_mutating_execution` 等三项合同。127 的完整桥接回归 246/246 通过。
- 原件：本机 `dist/validation/remote-side-model-20261104/verification.json` 及 `browser-before/after`、原生字段/轮次快照。此项仅需管理端更新；本轮没有替换在用服务，不把隔离验证当作手机已生效。

## 4. 后续迭代的核对顺序

1. 按受影响功能选择本清单条目，记录对应 R 用例及本次代码/运行资源版本。修改前复现，或明确已有原件能证明哪条因果链。
2. 保留用户操作顺序和实际入口：先发送再往返、真实隐藏/恢复、异步等待期间展开侧栏等，不能用直接调用内部恢复函数替代。
3. 验证正常结果及该条的失败/恢复边界；检查准确会话、目标、队列或回执身份，不以按钮变化、HTTP 200 或相同文字替代业务事实。
4. 对性能问题记录分段耗时、重复次数、样本数与环境；对提示问题记录出现时刻。未定义的指标不自行编造成 SLA。
5. 更新“已通过子场景 / 待复测 / 尚未执行 / 待用户验收”和证据位置。仅相关修改触发复测，旧通过记录不删除；新版本也不自动继承旧通过。
