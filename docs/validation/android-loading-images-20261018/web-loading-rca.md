# Android 聊天首次加载与图片链路调查

## RCA 结论

- 状态：**部分确认**。已确认并修复共同网页代码中的历史聚合串行等待、首次加载提示过早消失、队列重绘反复创建图片节点，以及“存在失败未决回执时自动恢复旧输入覆盖进行中选图”的条件缺陷。不能据此断定 Android 与浏览器差异、用户现场缺图全部来自这些机制。
- 现象：按本次任务输入，Android 首次进入聊天时先出现最新活动，较早正文仍空白，队列图片未出现；同一聊天的浏览器正文和缩略图较快出现，浏览器截图自身也有自动重连。截图当时的 Android WebView、资源快照、HTTP/WS 记录均不可得。
- 直接原因：前端实时事件能先创建一条活动并触发渲染；只要消息列表不为空，原先的整屏历史加载提示就不再渲染。历史接口在全部轮次完成前不返回，队列图片则依赖另一个 thread 读取结果和后续图片请求。
- 根因：原生历史适配器每页取 3 轮，每轮最新 40 条消息；有旧页的轮次还补取正序第一页以投影用户输入。不同轮次原先串行等待；前端把“没有任何条目”作为显示首次加载提示的条件，未同时表达“实时条目已到，但首次历史仍未到”。
- 系统性根因：历史整页聚合返回与实时增量独立到达，而首次加载 UI 原先只处理空列表。队列状态渲染将展示图片与操作控件一起整体重建，连接/操作状态变化也会创建相同来源的新 `img`；图片接口要求重新认证并使用 `no-store`，没有持久缓存可补偿这一重绘行为。是否在用户设备上形成取消或重复下载，仍需真实网络记录。
- 关键因果链：选中聊天 → 并发请求 history/thread → WS 先到达实时活动 → 已有活动令原历史占位消失 → history 仍在顺序读取多轮消息 → 用户看到活动与空白；thread 返回队列图片引用 → 浏览器请求 `/api/images/{id}` → 连接/操作状态变化重绘队列 → 原先生成新图片节点。

## 已排除解释

- 候选解释：history 必须等待 thread 才开始。
  - 排除证据：前端两条请求原本并发；确定的顺序等待位于原生 history 的多轮聚合内部。
- 候选解释：已有一条实时活动就证明历史已加载完成。
  - 排除证据：实时事件可独立创建 turn；隔离夹具刻意挂起 history，仍能先显示该条活动。
- 候选解释：首次 `onopen` 的补读可以无条件合并到进行中的 HTTP 请求。
  - 排除证据：HTTP 快照生成后、WS 订阅之前发生更新时，该更新可能不在任何已订阅事件里。补读覆盖这一间隙；源函数反例证明最终应用了较新的 revision。因此最终代码保留首次补读和后续重连强制核对。
- 候选解释：当前前端使用长连接 SSE 占用图片请求槽。
  - 排除证据：当前流工厂两条分支均使用 WebSocket；这排除“当前页面明确选择 SSE”这一具体说法，不能替代设备 HTTP 协议、连接池和隧道链路实测。
- 候选解释：资源清单总大小约 6.4 MB，证明每次启动都会重下 6.4 MB。
  - 排除证据：总清单描述完整资源集，不代表更新差量。当前 release APK 与服务清单相同；本子任务只记录静态大小与版本，不把它当作重复下载证据。资源下载/更新由并行 Android 调查单独验证。

## 异常状态溯源

- 适用约束：在所选聊天首次历史尚未返回时，即使已有实时条目，也必须在聊天入口明确显示仍在读取；历史成功后该提示必须消失，失败时转成可重试状态，切换聊天后不得残留到其他聊天。
- 约束依据及状态：本次用户现象与主代理的明确修改边界；已确认。已有完成正文的轮次，活动折叠及真实分页入口必须保留，不得重新产生段落间的假加载行。
- 本次运行前提命中判定：隔离夹具命中；截图当时设备无法判定。
- 场景命中证据：history 响应在夹具中挂起，同时通过 WS 投入一条 reasoning 活动。
- 值判断：原来的 `historyInitialized === false` 仍成立，但原占位因 turn 已存在而消失，违反上述展示约束；有实时活动本身是合法状态，不应隐藏它。
- 值的实际来源与传播路径：`selectThread()` 清空历史并开始读取 → `receive()` 插入实时 turn → `renderMessages()` 读取 turn 数量与 `historyInitialized` → 原实现只对空列表显示加载。
- 最后满足约束的状态 → 首次违反点：选中聊天后空列表加载占位正确；收到实时活动后的下一次渲染首次移除必要提示。
- 调查边界与未知上游：不修改其他聊天、历史来源、鉴权、分页格式；截图时手机缓存版本和 WS/HTTP 时序不可追溯。

## 修复与防复发

- 直接修复：只有所选聊天尚未完成首次历史、列表已有实时条目且没有历史错误时，在消息区顶部显示“正在加载会话记录，已先显示实时活动…”。空列表继续使用原占位；失败继续使用原失败重试；成功和聊天切换沿原状态清理。
- 根因修复：不同轮次最多 2 个原生读取并发，以原页索引保存结果，再按原顺序组成完整响应。每轮 desc 后的 asc 上下文读取、消息缩页、游标、轮次状态、时间、归属检查及整页失败语义保留。原生适配版本 40 → 41，入口检查与导出一致。
- 图片修复：仅在同一设备和同一聊天内，对同一队列消息、同一附件描述复用原有图片节点；尚在加载或已成功解码的图片可以复用。已失败的图片允许下次渲染重新请求；来源变化、消息移除、设备/聊天变化都不复用。
- 选图恢复修复：`recoverFailedInput()` 已可靠保存旧失败输入并登记恢复记录后，若当前编辑框正在读取图片，就停止自动覆盖；恢复记录仍保留供后续人工取回。没有拦截真实聊天切换，也没有修改附件模块。
- 系统性防线：首次历史的完成状态独立于实时条目数量；图片的节点生命周期独立于队列操作控件。没有持久缓存图片，没有取消请求授权检查。
- 保留行为：80vw 侧栏、主题单按钮、16px 队列手柄、上下文单行 muted、独立授权卡草稿、`historyLoadingOlder`、完成活动内折叠补页均未回退；本子任务未修改 `style.css`、附件选择器或 Rust。
- 验证范围：源函数修改前 11/12（唯一预期不通过为目标并发 2），修改后 13/13；包含完整结果深度相等和 HTTP 快照/WS 订阅间隙反例。`node --check` 检查 app/native，`git diff --check` 检查对应文件均退出 0。

源函数验证在 Node VM 中执行实际 `nativeItemsPage()`、`enrichHistoryTurn()`、`historyPage()`、流初始化及刷新函数；原生 RPC、桌面会话元数据依赖由合成夹具提供。深度一致结论适用于该夹具的完整响应，不等于真实桌面 manager 的运行时验收，也不证明现有会话在所有并发时序下的绝对耗时。

## 选图期间恢复旧失败输入的条件缺陷

用户随后明确补充“选了图片，但编辑框没显示”。本项先只读追踪恢复链，再经主代理确认修改一行当前草稿自动恢复门禁。

- 前提：当前编辑框没有已完成的新文字/附件；有 send/create 的失败未决回执；新图片正在 `readImageFile()` 的异步步骤中，尚未 `attachments.push()`。
- 关键因果链：选图回调进入 `addFiles()` → `readingFiles = true`、捕获附件版本 → WebSocket 恢复后 `resolvePending()` 得到旧失败回执 → `recoverFailedInput()` 看到的当前附件快照仍为空 → `restoreDraft()` 调用 `setComposerAttachments()` → 附件版本递增 → 新图片读取完成后命中版本不一致并静默退出。
- 原因层次：直接原因是 `addFiles()` 为保护切换草稿而丢弃版本不匹配的读取；产生不匹配的机制缺陷是自动失败输入恢复没有把进行中选图当作当前输入；状态表达只包含完成附件快照，遗漏异步读取状态。真实聊天切换使用版本取消是正确行为，必须保留。
- 适用约束：在当前聊天、当前授权且选图仍进行时，旧失败回执不得自动替换当前编辑框；旧失败输入必须可靠保留，读取失败后允许用户手动恢复。主代理明确确认此约束。
- 场景判定：源函数受控复现命中；用户现场是否有失败未决回执仍**无法判定**。普通同授权恢复只会改变连接/禁用状态，不重置附件版本，不能把普通切后台一概判为根因。
- 对照：旧代码附件版本 0 → 1、最终 0 图、无 notice；新代码版本保持 0、最终 1 图、旧失败恢复记录仍为 1。读取失败后原“恢复输入”按钮可恢复旧输入，随后正常移除恢复记录。正常自动恢复、当前新文字/图片保护、真实切换取消旧读取均保留。
- 验证边界：`picker-resume-race-before.json` 的 6 个用例记录旧行为，`picker-resume-race-after.json` 的 8 个用例验证新行为；文件读取由可控 Promise 门控，因此不证明真实 Android URI、文件读取或图片解码成功。这些仍由附件/Android 调查覆盖。

- 修改后：`http://127.0.0.1:1484/#thread=11111111-1111-4111-8111-111111111111`
- 默认在普通 Chrome 中模拟 Android bridge 和无 SharedWorker，以隔离共同 JS 逻辑；加 `?shared=1` 可走 Chrome 自身的 SharedWorker 分支。它不等于 Android 真机。

## 未闭环项与下一步

- 缺失证据：截图时 Android WebView 版本、`typeof SharedWorker`、实际 transport、已启用本地资源快照版本与公网网络记录。

  - 对结论的影响：当前修复证明可避免无谓节点重建，不能据此认定真实缺图已完全修复。
