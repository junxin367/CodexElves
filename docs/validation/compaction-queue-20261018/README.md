# 压缩期间编辑与排队发送验证

2026-10-18。功能实现与定向验证完成；未提交、正式打包、安装、部署或操作真实聊天。

## 最终行为

- 网页及 Android 共用的普通编辑框在压缩期间可继续编辑文字、Skill 和图片。服务支持且原生压缩状态已确认时，发送默认进入原生队列。
- 原生读取确认的 pending 与本页未获回执的 pending 分开处理，不改写回执 `acknowledged` 的含义。unknown、旧身份或服务不支持时仍可写草稿，发送保持保护并说明原因。
- 压缩时空编辑框使用发送动作，不显示可用的停止动作；已发消息编辑、队列编辑/排序/引导、目标创建、模型切换、停止和重复压缩保留原门禁。
- 只有入队确认后才清理提交的草稿，发送期间后来输入的内容保留；失败或送达未知不会自动重发。
- 正常 running 状态继续只在消息区显示压缩状态，不新增重复黄条；异常、旧服务和待确认情形保留提示与恢复操作。

## 原生与接口

原生适配器升至 v45，服务声明 `capabilities.compactionQueueSend`。普通发送可使用布尔 `queueOnly`，目标、新建和其他操作不能携带此字段。原生实时检测到压缩时也会进入队列，避免滞后的页面抢先发消息。

复用已有 server/local 队列和原生调度器。已有 local 消息时不直接追加 server queue，避免插队；同 ID 在途请求合并，不同内容拒绝；未知入队结果只查询，不再次 add。普通 `sendState` 确认结果后释放已终态的未知身份记录，仍在途的记录不提前释放。

当前安装版真实 app-server 不按 `clientUserMessageId` 自动去重，因此不能仅依赖后端或网页按钮禁用。相关修复前证据、原生调度证据与本机版本摘要见 `native/native-report.md`。

浏览器共提交 6 次模拟消息：5 次携带 `queueOnly:true`（含 1 次明确失败），1 次普通发送未携带该字段；每次都有不同的回执 ID 和客户端消息 ID。另外只发起了 1 次模拟压缩，以验证未知回执保护，没有重发。

浏览器确认：原有队列顺序保留，纯图片显示在队列中，回执返回前可继续写下一份草稿，返回后新草稿未被覆盖；失败保留内容，原生已确认 pending 可以入队，unknown 与旧服务只放开编辑；压缩结束后普通控件恢复。图片测试使用测试 File 驱动生产粘贴处理，不是 Android 相册实测，也未修改系统剪贴板。

原生 app-server 使用独立临时配置与用户目录，模型流量仅发往本机无认证 mock，不返回工具调用。实际队列、压缩和轮次调度参与运行；附件准备与 manager 映射为合成适配。没有真实账号模型推理、图片物化、实体手机或正式环境验收。
