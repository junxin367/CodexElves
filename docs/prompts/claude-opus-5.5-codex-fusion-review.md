## Opus 5.5 实际走哪一组提示词

本机内嵌能力表给 `claude-opus-5-5` 标记了：

```text
lean_prompt
opus_5_5_prompt_bundle
adaptive_thinking
rejects_disabled_thinking
default_effort = medium
```

主组装函数是 `chunk-hvqemeay.js` 中的 `IE`。`Dq` 选择简版或标准版；在没有覆盖的情况下，Opus 5.5 的 `lean_prompt` 能力会选择 `BQn` 简版基础提示词，再追加由模型能力、工具集合、运行模式和开关决定的其他段。

标准长版的 `IQn`（任务执行）、`OQn`（操作边界）、`LQn`（工具使用）等与简版是替代关系，不能把二进制里搜索到的所有规则同时拼进去，再声称是 Opus 5.5 的默认原文。环境变量、能力覆盖、提示词模型映射和提示词段解析器还可能改变实际选择。

同样需要区分 `opus_5_prompt_bundle` 与 `opus_5_5_prompt_bundle`。代码中的“减少子代理使用”段 `kkt` 受前者约束，不能仅因名称相近就判定它在 Opus 5.5 中默认启用。本次融合草案采用用户明确的子代理习惯，这是有意定制。

## 当前草案的适配边界

当前草案使用 `# Harness`、`# Communicating with the user`、`# Doing tasks`、`# Executing actions with care`、`# Session-specific guidance`、`# Context management`、`# Delivering work`、`# Reporting outcomes` 分段。保留原文的英文行文与 Markdown 形式，不再以中文 XML 区块重写全部规则。默认用中文回答用户，单独通过一句语言规则指定。

针对运行环境的修改集中在 `Harness`：显示界面改为 Codex，工具名和参数服从当前会话定义，权限拒绝不被一概解释为用户主动拒绝，来源和权限以宿主消息为准，文件引用使用宿主支持的链接格式。Claude Code 的 CLI 快捷方式、hook 假设和源码插值变量不带入成品草案。

针对用户习惯的补充集中在授权与 `Session-specific guidance`：任务范围内不反复确认；Git 提交、推送和发布等需要明确授权；保留已有改动；Windows 默认 `pwsh`；搜索遵守忽略规则；技能按实际触发规则使用；子代理仅在用户明确要求或适用技能明确要求且宿主允许时启用。

`jQn` 本来是条件段，`IQn` 本来属于标准长版。为满足完整交付和控制修改范围的要求，草案主动选入了这些文本；这是一项明确的组合选择，不能称为 Opus 5.5 原生默认配置的逐字复制。原文提取文件保持独立，后续可继续逐段比较。

本次静态校验确认 10 处保留文本与提取原文一致，包括安全说明、上下文管理正文、交付正文、结果报告及选用的任务规则；`jQn` 的首句仅移动位置。草案没有遗留 XML 区块或 `${...}` 插值，Markdown 标题和差异空白检查通过。尚未进行真实模型行为测试。

## 当前代理需要配套调整的部分

以下为本次源码检查所得，不是已经实施的修改。

配置选择继续保持：

```text
非空的模型级提示词
    否则：非空的供应商级提示词
    否则：原请求的默认基础提示词
```

这里的优先级仅描述选择哪份可配置基础文本，不表示模型配置可以抹去宿主权限、工具协议或项目规则。当前模型与供应商选择逻辑位于 `crates/codex-elves-core/src/settings.rs:221`。

当前 `apply_system_prompt_override_to_responses_request` 位于 `crates/codex-elves-core/src/protocol_proxy.rs:236`。存在覆盖时，它会改写 `instructions`，并调用 `remove_responses_system_messages`。后者位于同文件第 341 行，会递归删除输入中的 `system` 和 `developer` 消息。这可能一并删除运行说明。新的提示词无法恢复已经被代理删掉的具体上下文。

建议的组装约定：

```text
选中的模型基础文本
    + 保留来源与顺序的宿主运行约束
    + 按宿主规则加载的项目说明、技能和环境上下文
    + 当前用户任务与必要会话历史

当前工具定义与工具返回值按协议独立传递
```

实现时先核对进入代理的请求结构，确认 `instructions` 中哪些内容由基础提示词生成器拥有。只有来源明确的基础部分可以替换；不能仅凭一段自然语言看起来像模型身份就删掉它。如果当前 `instructions` 已混入不可区分的运行约束，需要先建立来源标记或在生成处拆分。

随后移除按角色批量清空输入的行为，保留独立的开发者与系统运行消息。若确有重复注入，只对来源明确、可证明重复的片段去重。模型别名解析前后需保持同一配置选择语义；供应商回退、无覆盖、压缩和提示词优化路径也要单独核对。

当前 Anthropic 转换入口 `responses_to_anthropic_messages_with_diagnostic_id` 位于同文件第 953 行。它把 `instructions` 与从输入提取的系统文本合并进 Anthropic `system`，并另外转换工具。把文本保留下来并不等于原协议的角色层级自动原样保留；需要明确说明各段来源与适用范围，验证冲突时的行为，不能宣称标签能建立协议级隔离。

建议保留同一会话中稳定的基础提示词与工具集合，迭代时用独立新会话比较效果。此次没有修改现有会话或模型配置。
